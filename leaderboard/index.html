Crash test leaderboard: does one approved payment run twice after a crash?

A person approves one payment. The tool pays. The process is killed right after, before the framework saves its progress. A new process resumes the way the framework documents. We count the payments.

The result

With each framework's documented default resume, every crash run made 2 payments (110 of 110 runs) and every control run with no crash made 1 (110 of 110). With the same agents and Call4Agents 0.7.3 on the tool, every crash run made 1 payment (150 of 150): the agent stopped and asked a person instead of paying again.

What this means, and what it does not

This is a measured fact about the default setup, not a bug report. Doing an action and saving that it was done are two separate steps in any system that saves progress after doing work. If the process dies between them, a resume runs the action again: at-least-once execution. Several of these frameworks say so in their docs and ask that tools with side effects be idempotent. A tool that sends a stable idempotency key to a provider that honours it would also make 1 payment here, with any framework.

FrameworkWhat its docs say about resume and side effects (read 19 Nov 2026)
LangGraphA node restarts from its beginning when resumed; side effects before interrupt must be idempotent. Interrupts
Pydantic AIDurable-execution integrations replay completed steps from a journal and retry the one in flight. Deferred tools, Durable execution
OpenAI Agents SDKAn approval lets a tool call run; it does not guarantee exactly-once execution, and resuming from an older approved state can run the tool again; it suggests a stable idempotency key per action. Human-in-the-loop
Google ADKTools run at least once and may run more than once when resuming; modify the tool to check for and prevent duplicate runs. Resume stopped agents
Microsoft Agent FrameworkWe found no sentence on running a tool again after a restore. Corrections welcome. Checkpoints

With Call4Agents the resumed call raised EffectInDoubt in every crash run: the record says the payment started and has no result, so it does not pay again by itself and waits for a person (or for a lookup at the provider, reconcile=, which these runs do not use). The run does not finish on its own.

Method

  1. The agent asks to call pay(amount=10, to="alice"), a tool that needs approval. The run pauses and the framework saves its state the way its docs say.
  2. A person says yes (scripted). The tool appends one line to a local payments file and the process is killed with os._exit right after, so no cleanup code runs.
  3. A new process resumes from what was saved, the way the framework documents (last column of the table).
  4. The payments file is counted. The count comes from the file, never from what the framework reports.

Fake models, so no API key, no network and no real money. Each phase is a separate process and each run a new temp folder. Each framework has its own Python environment; the exact packages are in pip_freeze/. The control run is the same with no kill. The Call4Agents runs are copies of the same scripts with the tool wrapped as c4a.effect(pay, name="pay", approval=True), the record kept outside the framework's state, the run id taken from the framework's resume id; every change is in scripts_guarded/DIFF.txt.

How to correct a row

If a script does not use your framework the way its docs say, or a newer release changes a result, open an issue or a pull request on github.com/salahmakboul/call4agents with:

  1. the my-rerun-... folder that rerun_row.py wrote, with the run files unchanged;
  2. your pip freeze, Python version and operating system;
  3. one line on what you changed and why, ideally with a link to the framework's docs.

We rerun it, reply in the thread with our files, and if they agree the row is replaced, with a link to your issue. A different configuration (a durability mode, a retry policy, a durable-execution add-on) is welcome as an extra row next to the default one; the default row stays, because that is what a new user gets.

Monthly rerun

We rerun every row once a month with the newest release of each framework, and add the result here with its date; older results stay listed. Next rerun: 1 December 2026.

Limits

  • One Windows 10 machine, Python 3.12.10. No Linux or macOS run in this table yet.
  • One tool, one fake model, one crash point (inside the tool, right after the payment). Other crash points, real models and multi-step plans are not covered.
  • Defaults only. Durability modes, retry policies and durable-execution add-ons were not turned on.
  • A fake payments file with no idempotency keys. A real provider that drops duplicate requests by key changes the result for every row.
  • 10 to 30 runs per case show that an outcome happens. They are not a rate.
  • We maintain Call4Agents, the library in the last result column. The scripts and every run file are public so anyone can check or correct this page.

More scenarios (a lost answer, two workers resuming at once, an edited approval, a "no" after a "yes") for three of these frameworks are in the open benchmark. To run the same kind of test on your own agent in CI, see call4agents crashtest and the GitHub Action in the README.
