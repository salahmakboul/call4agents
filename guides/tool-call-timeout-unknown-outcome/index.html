My agent's tool call timed out. Did it run?

A timeout or crash does not tell you whether the action happened. What we measured with real process kills, why a read-back can mislead you, and what to do instead.

The short answer

You don't know, and retrying is how you find out the expensive way. After a timeout or a crash, an action has three possible states: done, not done and unknown. Most duplicate emails and double payments come from treating unknown as not done.

Why "check first, then retry" can fail

The usual advice is to read the state back from the provider and retry only if the action isn't there. A read that finds nothing can simply be behind. We tested this in plain Python with a fake provider that commits at once and shows the commit to reads 200 ms later. The worker sends and dies, then recovery reads back and retries on "not found". 20 runs each:

Read back afterCommits
0 ms2
100 ms2
300 ms1

The check worked only when it waited longer than the lag. Most providers don't publish a worst-case lag, so "not found" is weak evidence unless the read is strongly consistent.

Three more ways it goes wrong

These are small tests with fake services and real process kills, not production numbers. All 26 results are in an open dataset on Hugging Face (CC BY 4.0).

SituationWeak designStronger design
A "started" record, then a crashInside the step's transaction: 2 effects in 10 of 10 runsCommitted on its own before the tool: 1 effect
A worker stalls past its lease, then wakes upLease only: 2 sends in 20 of 20 runsGeneration check at the record: 1 send
A used approval, then a restartKept in memory: 2 effects in 10 of 10 runsDurable store with a unique key: 1 effect

What to do instead

  1. Write a record before the tool runs, and commit it on its own. Then a crash leaves evidence that the call began.
  2. Keep "unknown" as a real state. Don't turn it into a failure, because a failure invites a retry.
  3. Settle it with strong evidence: an idempotency key the provider honours, a strongly consistent read, or a person.
  4. Keep your keys stable. If a key is built from arguments and the model invents a new reference ID, the key changes. In one test that paid twice; a key fixed on the business action paid once.
  5. Test it by killing the process. A handler that throws is kinder than a real crash, because cleanup code still runs.

See what your own agent does

This kills a Python agent at every step, restarts it and lists what ran twice. Your agent doesn't need to use our library first. The command is experimental and the actions really run, so use test accounts.

pip install call4agents
call4agents crashtest your_agent.py

The fixes above work with or without Call4Agents. It is one open-source way to do them in Python.
